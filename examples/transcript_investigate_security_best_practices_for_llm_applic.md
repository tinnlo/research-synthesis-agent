### Final Research Report

# Security Best Practices for LLM Applications

## Executive Summary

Security for large language model (LLM) and broader generative AI applications is now a full‑stack concern that spans data, models, tools/agents, and infrastructure. The research corpus converges on a few anchor frameworks—especially the OWASP Top 10 for LLM Applications and the broader OWASP GenAI project, NIST AI Risk Management concepts as interpreted by industry, and MLSecOps / secure MLOps guidance—as the organizing backbone for best practices [1][2][16][18][31][33][34]. Across sources, the dominant risks are prompt injection and data exfiltration, sensitive information disclosure, supply‑chain and model integrity issues, unsafe tool / function calling, and insecure deployment environments [1][4][6][7][10][16][19][21][33][34].

Best practices are best understood across the LLM lifecycle: design, development, deployment, and operations/monitoring. In the design phase, threat modeling, data classification, and architectural choices (e.g., RAG vs fine‑tuning, degree of agent autonomy) strongly influence the attack surface [1][16][19][31][33]. During development, recurring recommendations include robust prompt and tool design, input/output filtering, privacy‑preserving data handling, secure supply‑chain practices, and adversarial testing / red teaming [1][3][5][9][12][16][18][19][31][33][35]. Deployment best practices focus on network isolation, secrets and key management, tenant isolation, hardened runtime environments, and careful integration with external tools and APIs [14][15][18][19][21][26][27][28][30][33][34]. Finally, effective operations require continuous monitoring, abuse detection, structured logging with privacy safeguards, incident response plans, and periodic red teaming and control reassessment [2][10][19][26][28][31][32][33][35].

The literature also highlights important trade‑offs: stronger logging vs privacy, stricter guardrails vs model utility, and deep defense‑in‑depth vs cost and complexity [2][18][26][31][33]. Supply‑chain assurance for models and prompts, verifiable safety for tool‑using agents, and robust defenses against sophisticated prompt injection remain active research areas with incomplete solutions [16][17][20][23][24][25][31]. Nonetheless, there is broad consensus that organizations can significantly reduce risk by combining established security engineering practices with LLM‑specific controls, anchored in OWASP/NIST‑aligned frameworks and implemented across the entire lifecycle.

## 1. Frameworks, Threat Models, and Cross‑Cutting Themes

### 1.1 Core Frameworks and Guidance

- **OWASP Top 10 for LLM Applications (2025)**  
  Provides a prioritized list of LLM‑specific risks (e.g., prompt injection, sensitive information disclosure, supply‑chain vulnerabilities, data/model poisoning, improper output handling, excessive agency, overreliance, unbounded consumption), along with example attacks and mitigations [1][4][16]. It is explicitly intended as a practical guide for developers, security engineers, and architects.

- **OWASP GenAI Security Project & LLM Security Guides**  
  Extends beyond the Top 10 into deployment checklists, RAG and agentic AI guidance, and solution landscapes. Community resources like the LLMSecurityGuide aggregate OWASP LLM and Agentic Top 10, plus concrete tools for red teaming, monitoring, and guardrailing [3][5].

- **NIST‑aligned Risk Management & MLSecOps**  
  Industry sources map LLM risks to NIST AI Risk Management concepts and to OWASP ML Top 10, emphasizing functions like GOVERN/MAP/MEASURE/MANAGE and integrating security into MLOps (MLSecOps) pipelines [2][18][19][31][33]. OpenSSF’s MLSecOps whitepaper maps threats (data poisoning, model theft, AI supply‑chain attacks) to each MLOps stage and calls for security‑by‑design across the pipeline [18].

- **Platform‑specific Security Guidance**  
  Cloud and AI providers (Azure, AWS, GCP, OpenAI, Anthropic, Google AI) document patterns for network isolation, identity, secrets, logging, and abuse detection tailored to LLM workloads [26][27][28][29]. These complement generic AI security guidance from industry and government bodies [17][19][30][33][35].

### 1.2 Dominant Risk Themes

Across frameworks and case studies, several recurring risk classes emerge:

- **Prompt Injection and Output Manipulation** – Ranked #1 in OWASP’s LLM Top 10 and seen in >70% of assessed deployments in some audits [1][10]. Attacks include direct and indirect prompt injection, template manipulation, and jailbreaks leading to data exfiltration, unsafe tool use, and policy bypass [6][7][8][9][10].

- **Sensitive Information Disclosure & Privacy** – LLMs can leak training data (memorized PII/PHI), contextual data from RAG or tools, or secrets embedded in prompts/logs. Multi‑tenant setups exacerbate cross‑tenant leakage risks [1][12][14][33][34].

- **Supply‑Chain and Model Integrity** – Backdoored or poisoned models, tampered fine‑tuned weights, malicious dependencies, and compromised prompt libraries are key concerns. LLM03/LLM04 in OWASP explicitly cover supply‑chain and poisoning risks [1][16][17][18][19][20][34].

- **Unsafe Tool / Function Calling and Excessive Agency** – LLM agents issuing network, filesystem, code‑execution, or financial operations without adequate constraints can cause severe real‑world impact; OWASP calls this “Excessive Agency” and “Insecure Plugin Design” [1][9][21][22][23][24][25][34].

- **Deployment and Infrastructure Weaknesses** – Weak identity and access management (IAM), exposed endpoints, poor secrets handling, and insufficient monitoring/logging create paths for abuse and lateral movement [18][19][26][27][28][30][33][34].

These threats drive the need for lifecycle‑oriented best practices described in the sections below.

## 2. Design‑Phase Best Practices

Design is where you set the security posture and constraints that are hardest to change later.

### 2.1 Threat Modeling and Risk Scoping

- **Perform LLM‑specific threat modeling**  
  Incorporate OWASP LLM Top 10 and ML Top 10 into standard STRIDE or attack‑tree models, explicitly considering:
  - Prompt injection (direct and indirect), jailbreaks, and data exfiltration [1][6][7][8][10][31].
  - Training data extraction, membership inference, and PII leakage [12][14][18][33][34].
  - Supply‑chain compromise of models, data, libraries, and prompts [16][17][18][20][34].
  - Tool/agent misuse and escalation via external APIs, plugins, and RAG connectors [1][9][21][22][23][24][25][33][34].

- **Map risks to business impact and regulatory context**  
  Regulated sectors (healthcare, finance, government) must align with HIPAA, GDPR, SOC 2, and sector‑specific requirements; platform guidance stresses VPC‑isolated deployments, PHI‑aware guardrails, and documented model catalogs for regulated use [2][14][15][27][33].

### 2.2 Data Classification, Minimization, and Privacy Architecture

- **Classify data and define what may reach the model**  
  Identify PII, PHI, financial data, trade secrets, and high‑sensitivity corp data. Design policies for:
  - What can be used for training vs inference.
  - What can be sent to external API‑hosted models vs kept on‑prem/private [11][12][13][14][15][33][35].

- **Minimize and transform sensitive data**  
  Recommended controls include:
  - Anonymization/pseudonymization and tokenization of PII/PHI before training or inference [11][12][13].
  - Redaction / DLP filters at gateway level to strip credentials, IDs, and secrets from prompts [11][12][15][33].
  - Avoiding inclusion of secrets or long‑lived credentials in system prompts or examples [9][11][33][34].

- **Architect for separation of concerns**  
  - Separate training data pipelines from inference traffic; treat training corpora as high‑risk assets with strong access control and auditing [12][13][18][33][35].
  - For multi‑tenant SaaS, design explicit tenant isolation for both storage and retrieval layers to prevent cross‑tenant leakage in RAG and fine‑tuned models [14][33].

### 2.3 Model and Retrieval Strategy Choices

- **RAG vs Fine‑Tuning vs Hosted APIs**  
  - RAG reduces the need to embed sensitive data in model weights but introduces retrieval‑layer attacks (poisoned documents, untrusted content treated as instructions) [7][10][12][19][33].
  - Fine‑tuning on sensitive data increases memorization and membership‑inference risk; requires stronger privacy controls and potentially differential‑privacy techniques [12][13][14][18][33].
  - Hosted API models (OpenAI, Anthropic, Gemini, etc.) reduce some infrastructure burden but require strict data‑handling agreements (no‑training clauses, deletion SLAs) and network controls [11][15][26][27][33].

- **Agent Autonomy and Tooling Scope**  
  Design decisions on how autonomous agents are, what tools they can call, and which actions require human approval are central to risk. OWASP flags “Excessive Agency” as a top risk; research on safe tool use advocates configurable autonomy with explicit hazard constraints and human‑in‑the‑loop for high‑impact actions [1][21][23][24][25][28][31][33].

## 3. Development‑Phase Best Practices

### 3.1 Secure Prompt, Template, and Tool Design

- **Harden system prompts and templates**  
  - Keep system prompts minimal, avoid embedding secrets or sensitive business logic; treat them as high‑value assets subject to versioning and access control [1][3][5][9][20][33].
  - Use explicit instruction hierarchies and delimiters to separate system, tool, and user content; OWASP and industry guidance emphasize that clear boundaries reduce prompt injection effectiveness [1][9][10][19][31][33].

- **Defend against prompt injection and data exfiltration**  
  Common mitigations across sources:
  - Input filtering and semantic validation to detect jailbreak patterns, override phrases (“ignore previous instructions”), and embedded instructions in retrieved documents or external content [1][6][8][9][10][19][31][33][34].
  - Output validation / post‑processing to block restricted content, secrets, and unsafe tool invocations even after generation [1][6][8][9][10][19][33][34].
  - Policy engines external to the model so that prompts cannot override security rules [6][10][19][23][25][33].

- **Principle of least privilege for tools and plugins**  
  - Design tools with narrowly scoped capabilities and tokens; avoid generic “code execution” or unrestricted browser/file tools where possible [9][21][22][24][25][33][34].
  - Enforce per‑tool authentication, authorization, and parameter validation; treat LLM‑generated tool arguments as untrusted input [9][21][22][24][33][34].
  - Research frameworks like MiniScope propose formal least‑privilege authorization for tool‑calling agents, computing minimal permissions for a given plan and prompting users when additional privileges are needed [24].

### 3.2 Supply‑Chain and Model Integrity Controls

- **Model provenance and verification**  
  - Maintain a registry of approved models, including version, source, training provenance, and security review status [16][17][18][19][20][33][34].
  - Verify integrity of downloaded or shared models via checksums, hashes, and digital signatures; prefer trusted registries and signed artifacts [16][17][18][19][20].

- **Secure dependencies and ML toolchains**  
  - Apply standard software supply‑chain practices (SBOMs, dependency scanning, signed containers) to ML libraries and data pipelines [17][18][19][20][34].
  - Recognize AI‑specific supply‑chain risks: backdoored pre‑trained weights, poisoned fine‑tuning datasets, tampered prompt libraries. OWASP LLM03 and Microsoft’s AI pipeline guidance both emphasize these vectors [1][16][17][19][20][34].

- **Data and model poisoning defenses**  
  - Vet training/fine‑tuning data sources; apply data quality checks, anomaly detection, and provenance tracking to detect poisoning [16][17][18][19][33][34].
  - Use staged evaluation on held‑out datasets and targeted tests for backdoor triggers or biased behaviors [17][18][19][31][33].

### 3.3 Privacy‑Preserving Data Engineering

- **Safe handling of PII/PHI in training and evaluation**  
  - Strong encryption in transit and at rest for datasets and model artifacts (e.g., AES‑256, KMS‑backed storage) [11][13][14][15][17][26][30][33][35].
  - Access controls (RBAC/ABAC, MFA) over data stores and model endpoints; comprehensive audit trails [11][13][14][15][18][26][27][33][34].
  - Data minimization and retention limits; auto‑expiry for transient context storage where possible [11][12][13][14][33].

- **Mitigating training‑data leakage**  
  - Avoid training on raw production logs or user prompts containing unredacted PII; scrub or aggregate prior to use [11][12][13][14][33].
  - Consider techniques to reduce memorization and membership‑inference risk (e.g., regularization, DP training) in high‑sensitivity contexts, though operational guidance here is still emerging [12][14][18][31][33].

### 3.4 Testing, Red Teaming, and Evaluation

- **Adversarial testing focused on LLM‑specific threats**  
  - Traditional SAST/DAST are insufficient; guidance calls for LLM‑specific runtime testing, including prompt injection, jailbreaks, RAG poisoning, and tool‑misuse scenarios [2][3][5][10][18][19][31][32][33][35].
  - Use automated red‑team tools and fuzzers aligned to OWASP/NIST taxonomies (e.g., frameworks enumerated in LLMSecurityGuide) [3][18][19][31][33].

- **Security gates in CI/CD**  
  - Integrate security checks into the MLOps pipeline: supply‑chain scans, model integrity checks, red‑team tests, and policy compliance checks as pre‑deployment gates [18][19][28][31][33][35].
  - Azure and Microsoft guidance explicitly recommend red teaming against MITRE ATLAS and OWASP LLM Top 10 before release [19][28].

## 4. Deployment and Runtime Hardening

### 4.1 Network Segmentation and Endpoint Exposure

- **Private connectivity and segmentation**  
  - Use private endpoints / VPC peering for LLM services (e.g., Azure OpenAI private endpoints), removing or restricting public internet exposure where feasible [26][28][33].
  - Implement network segmentation with security zones or micro‑segmentation between app tiers, model serving infrastructure, data stores, and external integrations [26][27][30][33].

- **Perimeter and transport protections**  
  - Enforce TLS everywhere; deploy WAFs, next‑gen firewalls, IDS/IPS, and DDoS protections at boundaries [26][27][30][33][34].
  - For AI‑specific traffic, route through a centralized AI gateway that enforces DLP, rate limiting, input/output filtering, and logging [11][15][19][26][33].

### 4.2 Identity, Secrets, and Tenant Isolation

- **Strong authentication and authorization**  
  - Prefer managed identities (e.g., Azure Entra managed identities) over static API keys where supported [28][33].
  - If keys are required, store them in cloud‑native vaults (AWS KMS‑backed services, Azure Key Vault, GCP Secret Manager), rotate frequently, and scope them minimally [15][26][28][30][33][34].
  - Implement RBAC/ABAC for model endpoints, tools, and data stores; enforce per‑team or per‑tenant model catalogs in regulated environments [14][15][26][27][33][34].

- **Tenant and context isolation**  
  - For multi‑tenant SaaS, isolate tenants at the data, retrieval, and model‑config layers. Research highlights that fine‑tuning or RAG on multi‑tenant data without strong isolation can enable cross‑tenant data extraction [14][33].
  - Segregate session contexts; avoid cross‑session or cross‑tenant “memory” unless explicitly designed and secured (e.g., context segmentation, auto‑expiry) [11][14][33].

### 4.3 Runtime Guardrails and Tool‑Use Safety

- **Layered input/output controls**  
  - Deploy multi‑layer content filtering (pre‑prompt, pre‑tool, pre‑response) for harmful content, PII/PHI, and policy‑violating outputs [1][5][10][19][28][33][34][35].
  - Treat LLM outputs as untrusted: validate and sanitize before using them as commands, code, SQL, or API calls [1][9][21][22][23][24][25][34].

- **Safe tool and agent execution**  
  - Enforce least privilege at runtime for tools (scoped tokens, limited operations, constrained environments) and avoid generic tools that can execute arbitrary code or browse the open internet when data‑leak risk is high [9][21][22][24][25][33][34].
  - Use sandboxes (e.g., jailed containers, restricted interpreters) for code‑execution tools; apply rate limits, allowlists, and egress controls on network‑calling tools to prevent SSRF and data exfiltration [19][21][22][23][25][33][34].
  - Research systems (Towards Verifiably Safe Tool Use, AgentTrust, MiniScope) propose explicit hazard modeling, runtime safety evaluation, and deterministic interception of unsafe tool chains, particularly for multi‑step agents [23][24][25].

- **Human‑in‑the‑loop for high‑risk actions**  
  - Require human approval for operations like money movement, system configuration changes, external data transfers, or destructive file operations. Azure guidance suggests implementing this via workflow tools (Logic Apps, Power Automate) [9][19][28][31][33].

## 5. Operations, Monitoring, and Incident Response

### 5.1 Logging, Monitoring, and Abuse Detection

- **Structured, privacy‑aware logging**  
  - Log security‑relevant metadata (caller identity, tools used, resource IDs, error codes, guardrail decisions) while minimizing or redacting sensitive content from prompts and responses [11][14][18][26][27][31][33][35].
  - Maintain audit trails for access to models, data, and configuration changes; this is critical for regulated environments and post‑incident forensics [11][14][15][18][26][27][33][34].

- **Abuse and anomaly detection**  
  - Monitor for:
    - Unusual prompt patterns (e.g., known jailbreak strings, policy override attempts).
    - Abnormal tool‑use sequences (e.g., repeated data‑exfiltration attempts or outbound calls to suspicious domains).
    - Resource spikes indicating denial‑of‑service or unbounded consumption [1][7][10][19][26][27][28][33][34].
  - Some providers and tools employ ML‑based behavioral analysis to detect anomalous inference usage and potential exploitation [19][26][27][33].

### 5.2 Governance, Change Management, and Training

- **Security governance and ownership**  
  - Clear accountability: many guidelines recommend that AI system security fall under existing CISO / security leadership, not in a silo [2][19][30][31][33].
  - Establish policies for acceptable AI use, data handling, model selection, and agent autonomy; align with OWASP/NIST frameworks [2][18][31][32][33][34].

- **Secure change and configuration management**  
  - Treat prompts, model configs, and tool catalogs as code: version control, code review, change approvals, and rollback plans [3][18][19][20][31][33][35].
  - Incorporate lessons learned from incidents into updated threat models and controls [19][31][35].

- **Training and awareness**  
  - Train developers, data scientists, and ops teams on LLM‑specific risks (prompt injection, RAG poisoning, privacy leakage, supply‑chain threats) and safe patterns [2][5][18][31][32][33][35].
  - Provide end‑user guidance for internal copilots to reduce inadvertent data leakage and risky prompt behavior [2][11][33].

### 5.3 Incident Response for LLM Systems

- **Preparedness and playbooks**  
  - Extend incident response plans to cover LLM‑specific events:
    - Prompt‑injection‑driven data exfiltration.
    - Discovery of backdoored models or poisoned datasets.
    - Cross‑tenant data leaks in multi‑tenant RAG systems.
    - Misuse of tools by agents leading to external impact [1][7][10][16][17][19][31][33][34].
  - Define containment actions (e.g., disabling specific tools, rolling back model versions, revoking credentials, isolating tenant data) and communication procedures.

- **Continuous improvement**  
  - Post‑incident reviews should feed back into design and development (e.g., updating guardrails, tightening least‑privilege scopes, improving monitoring rules) [19][31][35].

## Key Insights

- **Lifecycle, not point solutions**  
  Security for LLM applications must be integrated across design, development, deployment, and operations. Point controls (e.g., a single prompt filter) are insufficient against systemic risks like supply‑chain compromise or multi‑step agent exploits [18][19][31][33][34][35].

- **Defense‑in‑depth around prompt injection and tool use**  
  Prompt injection is the most common and impactful exploit, especially when combined with tools, RAG, and plugins. Effective defenses combine robust prompt and template design, semantic input/output filtering, strong tool least‑privilege, sandboxing, and human‑in‑the‑loop for high‑risk actions [1][6][7][8][9][10][19][21][22][23][24][25][33][34].

- **Data privacy and multi‑tenant isolation are central**  
  PII/PHI risks are amplified by LLM memorization, RAG over sensitive corpora, and multi‑tenant architectures. Consistent themes include encryption, data minimization, careful training data selection, tenant‑aware retrieval, and privacy‑aware logging [11][12][13][14][15][18][26][33][35].

- **Supply‑chain and model integrity need structured governance**  
  LLM supply chains (models, data, prompts, libraries) are opaque and complex. Best practices emphasize model registries, provenance tracking, signed artifacts, dependency scanning, and AI‑specific supply‑chain governance—areas where many organizations are currently immature [16][17][18][19][20][32][33][34].

- **Research is rapidly evolving on verifiable safety for agents**  
  Academic work on least‑privilege frameworks and runtime interception for tool‑using agents points toward more deterministic safety guarantees, but integration into mainstream tooling is still early [23][24][25][31]. Production systems currently rely heavily on probabilistic guardrails and manual review.

## Limitations and Open Gaps

- **Lack of mature, standardized metrics and benchmarks**  
  While OWASP and NIST provide taxonomies, there is limited consensus on quantitative security metrics and standardized benchmarks for LLM system robustness, especially for complex agent workflows [18][31][33].

- **Incomplete solutions for advanced prompt injection and RAG poisoning**  
  Defenses against indirect prompt injection (e.g., poisoned documents, emails, or web pages) and sophisticated RAG poisoning are still evolving; many sources acknowledge there is “no silver bullet” and that creative attackers can often bypass current filters [6][7][9][10][19][31][33].

- **Operationalizing privacy‑preserving training at scale**  
  While risks like membership inference and training‑data extraction are documented, practical large‑scale deployment of differential privacy or other strong privacy guarantees in commercial LLMs remains limited in public guidance [12][14][18][31][33].

- **AI supply‑chain visibility and attestation**  
  Model provenance, dataset lineage, and prompt library integrity are difficult to verify in practice, especially when relying on third‑party or open‑source models. Research and tooling for AI‑specific SBOM/AIBOM and attestation are still emerging [16][17][18][19][20][33][34].

- **Trade‑offs between security, utility, cost, and privacy**  
  The literature explicitly notes conflicting recommendations (e.g., extensive logging for forensics vs minimizing stored data for privacy) and the resource costs of deep defense‑in‑depth, especially for smaller organizations [2][18][26][31][33]. Risk‑based decision frameworks are recommended but not yet standardized.
